# Contributing

## Issues

Work is tracked in GitHub issues, structured as **epics → sub-issues**:

- **Epic** (`type:epic`): one per module or area. It states the goal and definition of done. Its work items are GitHub sub-issues.
- **Work item** (`type:feature`, `type:chore`, `type:docs`, `type:bug`): roughly one PR, with acceptance criteria. Every work item is a sub-issue of exactly one epic (bugs may stand alone).

Use the issue forms (Epic / Feature / Chore / Bug); blank issues are disabled. The forms in `.github/ISSUE_TEMPLATE/` are generated by `task gen` from `tools/modgen/templates/issue-*.tmpl`; the scope list is defined once and derived from the module manifests plus the areas in `tools/modgen/render.go`, so new modules appear automatically.

With Claude Code, the `/issue` skill (`.claude/skills/issue/`) drafts new issues and refines existing ones following these conventions.

### Definition of Ready

An issue is ready to be picked up when every check for its type holds. Refine it (or ask on the issue) before starting work otherwise; the `/issue` skill runs these checks on drafts and refinements.

**Work items** (`type:feature`, `type:chore`, `type:docs`):

- [ ] The body follows the issue form for its type (Feature: Context, Changes, Acceptance criteria, Notes; Chore / Docs: Context, Acceptance criteria, optionally Changes and Notes).
- [ ] *Changes* (where present) names real paths per layer (**Proto** / **Backend** / **UI**), e.g. `modules/chat/service/src/kb_chat/server.py`, not just "the chat backend".
- [ ] Every acceptance criterion is a `- [ ]` checkbox that can be observed or tested (a command, a UI behaviour, a file that exists), not "works well" or "is improved".
- [ ] It fits in about one PR. Bigger work is split into several sub-issues of the same epic.
- [ ] Labels are complete: exactly one `type:*`, exactly one scope (`module:*` / `area:*`), a `lang:*` for every stack touched, and `api-change` when a `.proto` changes.
- [ ] A milestone is set.
- [ ] It is a sub-issue of exactly one epic and ends with `Part of #<epic>`.
- [ ] Dependencies and open questions are listed under *Notes* with issue links (`Depends on #n`; also recorded as *blocked by* on GitHub). No open question blocks the work.

**Epics** (`type:epic`):

- [ ] *Goal* says what is true when the epic is done and names the code locations (`modules/<id>/…`, `platform/…`).
- [ ] *Definition of done* is a list of `- [ ]` checkboxes.
- [ ] No milestone (epics span phases).
- [ ] At least one sub-issue.

**Bugs** (`type:bug`): steps reproduce the problem on `main`, expected vs. actual behaviour is stated, labels have one type and one scope (or the scope is still being triaged), and a milestone is set once the fix is planned.

### Labels

| Group | Labels | Meaning |
|---|---|---|
| type | `type:epic` `type:feature` `type:chore` `type:docs` `type:bug` | Kind of work |
| scope | `module:document` `module:ingestion` `module:chat` `module:llm` `area:platform` `area:ui-shell` `area:infra` | Where it lives (one per issue) |
| lang | `lang:go` `lang:python` `lang:ts` | Stacks touched |
| contract | `api-change` | Changes a `.proto`: run `task gen`, mind `buf breaking` |

### Milestones

Work items are planned into delivery phases via [milestones](https://github.com/ChristophBe/kb/milestones); see there for the current phases and their goals. Epics span phases and get no milestone.

## Architecture decisions

Significant decisions are recorded as ADRs in [`docs/adr/`](docs/adr/README.md); the [architecture overview](docs/architecture/overview.md) shows how modules and infrastructure fit together. A PR needs a new ADR (copy `docs/adr/template.md`) when it:

- adds a module,
- adds infrastructure (a database, broker, external service or deployment component),
- adds or changes a cross-module contract pattern (a new way modules call each other or exchange events), or
- deviates from the module architecture or reverses an accepted ADR.

Update the overview diagrams in the same PR when services, ports or gRPC/NATS links change.

## Pull requests

- Branch from `main` and reference the issue (`Closes #123`).
- Title the PR in [Conventional Commits](https://www.conventionalcommits.org/) form (see below).
- Follow the [coding standards](docs/coding-standards.md).
- UI work follows the [UX and accessibility standards](docs/ux-standards.md) (WCAG 2.2 AA, design tokens, interaction patterns) and fills in the UI checklist of the PR template.
- A PR that adds or changes a user-facing feature updates the matching page of the [user manual](docs/user-manual/README.md) in the same PR, following its rules; a PR that removes a feature removes its description. PRs without a user-facing change tick the checkbox as not applicable.
- Run `task gen`, `task lint` and `task test` before pushing; the pre-push hook installed by `task setup` runs the fast versions for you.

### PR titles and commit messages

`main` has a semi-linear history: a PR is rebased onto the current `main` and lands as a merge commit whose title is the PR title and whose body is the PR description. Versions are derived from these commits: every push to `main` is released as `vX.Y.Z` with the bump in the table below (see [releases](docs/operations/releases.md)). The title follows [Conventional Commits](https://www.conventionalcommits.org/):

```text
<type>[(<scope>)][!]: <summary>
```

- **type**, one of:

  | Type | Use for | Version bump |
  |---|---|---|
  | `feat` | A new user-facing feature or capability | minor |
  | `fix` | A bug fix | patch |
  | `perf` | A performance improvement | patch |
  | `refactor` | A code change without behaviour change | patch |
  | `docs` | Documentation only | patch |
  | `test` | Tests only | patch |
  | `build` | Build system, tooling, dependencies | patch |
  | `ci` | CI workflows | patch |
  | `chore` | Anything else (housekeeping, config) | patch |

- **scope** (optional): a module id (`document`, `ingestion`, `chat`, `llm`, …: the `id` in `modules/*/module.yaml`), an area (`platform`, `ui-shell`, `infra`: the `area:*` labels), or `deps` for dependency updates. Usually the scope label of the issue the PR closes, without its prefix. Leave it out when the change spans several.
- **`!`** after the type or scope marks a breaking change and bumps the **major** version, whatever the type (e.g. `feat(chat)!: drop the v1 conversation API`). Explain the break in the PR description; a `BREAKING CHANGE:` footer in the PR description (the merge commit body) or in a branch commit has the same effect.
- **summary**: imperative, lower-case start, no trailing full stop.

Examples: `fix(document): reject empty uploads`, `feat(ui-shell): add a command palette`, `build(deps): bump vite to 7.1.0`, `docs: describe the home page`.

The `pr-title` workflow (`.github/workflows/pr-title.yml`) checks the title on every PR and re-runs when the title is edited; the allowed scopes are read from the module manifests and the `area:*` labels on each run. With Claude Code, the `/pr` skill (`.claude/skills/pr/`) derives the title from the closed issue's labels. Branch commits land on `main` unchanged, so they follow the same convention and should each be a coherent step.

The `pr-history` workflow (`.github/workflows/pr-history.yml`) fails when the branch is behind `main` or contains merge commits. Update a stale branch by rebasing (*Update branch → Update with rebase* on the PR, or `gh pr update-branch --rebase`), never by merging `main` in. The check does not re-run when `main` moves on, so make sure the PR shows the branch as up to date before merging.

### Dependency updates

[Dependabot](.github/dependabot.yml) opens version-update PRs every Monday, one grouped PR per ecosystem: Go (`go.mod` and `tools/go.mod`), Python (the uv workspace, `uv.lock`), npm (the pnpm workspace incl. the catalog in `pnpm-workspace.yaml`), Docker base images (`deploy/docker/*.Dockerfile`), the images pinned in `deploy/*.compose.yaml` and `modules/llm/compose.yaml`, and GitHub Actions. A release must be 14 days old before it is proposed (the same minimum age pnpm enforces). Titles read `build(deps): bump …` and release as a patch.

Versions Dependabot does not see are bumped by hand: the `uv` pinned in `deploy/docker/python.Dockerfile`, `SEMREL_VERSION` in `.github/workflows/release.yml`, the `go` directive in `go.mod` and `.python-version` (keep it in step with the `python` base image).

Handling an update PR:

- **Generated code.** Dependabot cannot run `task gen`. When a bump changes a generator (buf, sqlc, `protoc-gen-go*`, `grpcio-tools`, `@bufbuild/protoc-gen-es`), *Generated code is up to date* fails; check out the branch, run `task gen` and push the output as a `build(deps): regenerate code` commit.
- **Stale branch.** When `main` moves on, comment `@dependabot rebase` rather than using *Update branch*: Dependabot rebases its branch onto `main` (no merge commits, so `pr-history` passes) and keeps rebasing on conflicts. Once someone else has pushed to the branch, Dependabot stops rebasing it; then rebase it like any other PR, or comment `@dependabot recreate` to discard the extra commits.
- **Splitting.** If one update in a group breaks, comment `@dependabot ignore <dependency>` (or `… major version`) on the group PR, and fix it in its own PR.
- Dependabot PRs run CI with a read-only `GITHUB_TOKEN` and without repository secrets; the workflows need neither.

### Required checks

CI must pass on every PR. It fails when any of these fails:

| Check | Command |
|---|---|
| Generated code is up to date | `task check-gen` |
| No breaking proto changes | `buf breaking` against the base branch |
| Lint and type checks (all languages, no linter optional) | `task lint` |
| Unit tests | `task test` |
| Coverage minimum per component | `task test` (see [coding standards](docs/coding-standards.md#coverage)) |
| Go store integration tests against real Postgres | `task test:integration` |
| End-to-end smoke test: upload, processing and RAG chat against the composed stack | `task e2e` |
| Helm chart lints, installs on kind and passes the smoke test | job `helm` ([Kubernetes](docs/operations/kubernetes.md#how-the-chart-is-built)) |
| Accessibility lint (biome `a11y` rules as errors) | `task lint` |
| No axe violations in kit components | `task test` |
| WCAG AA contrast of every colour-token pair, light and dark | `task test` (see [UX standards](docs/ux-standards.md#automated-checks)) |
| PR title follows Conventional Commits | `.github/workflows/pr-title.yml` (job `pr-title`) |

All of these except the end-to-end smoke test (job `e2e`), the Helm install (job `helm`) and the PR title check (job `pr-title`) run in the `check` job of `.github/workflows/ci.yml`. Configure it as a required status check for `main` under *Settings → Branches* (or a ruleset): require a pull request, require status check `check`, and require the branch to be up to date. Branch protection on a private repository needs GitHub Pro/Team; until then the rule is enforced by convention.
